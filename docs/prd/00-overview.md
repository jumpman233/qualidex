# Qualidex PRD 拆分文档

> 来源：Qualidex PRD V1.4  
> 产品形态：Windows 本地桌面工具  
> 技术栈：Electron + electron-vite + React + TypeScript + SQLite + sqlite-vec + 本地 OCR + 云端文本 AI API

## 1. 项目背景

业务方手上存在大量人员资料文件，可能来自百度网盘同步目录、本地文件夹、历史压缩包或人工整理目录。资料类型可能包括：

- 身份证
- 学历证明
- 学位证明
- 执业执照
- 职业资格证
- 注册证书
- 培训证明
- 其他人员相关材料

这些资料可能存在以下问题：

- 文件夹结构不统一
- 文件名不规范
- 一个人的资料散落在多个目录
- 同一个人员可能拥有多份证书，且证书可能分散在不同文件或文件夹中
- 多个人员资料出现在同一个 PDF 或图片集合中
- 地区信息不稳定
- 类别信息可能涉及工程、环境、消防员等多个业务口径
- 查询时可能需要同时筛选多个类别，例如工程 + 消防员
- 证书名称不标准
- 同名人员难以区分
- 大量图片需要 OCR
- 人工查找人员和证书效率低

本工具目标不是做一个普通文件浏览器，也不是做 RAG 问答系统，而是一个本地人员资料治理工具。

## 2. 产品目标

### 2.1 核心目标

系统需要支持：

1. 选择本地资料目录并扫描文件。
2. 对图片 / PDF 等资料进行 OCR 或文本抽取。
3. 使用 AI 对 OCR 后文本进行结构化抽取。
4. 识别人员、地区、主类别、学历、证书等信息。
5. 将资料按统一规则复制到新的归档目录。
6. 对低置信度结果进入待确认流程。
7. 支持按地区、类别、学历、证书等条件查询人员。
8. 查询时类别支持多选，例如工程 + 消防员。
9. 支持导出 Excel、复制人员资料文件夹、生成后续可压缩的导出目录。
10. 支持新增部分文件夹。
11. 支持人员、文件、证书、归档信息的修改和软删除。
12. 支持重新生成归档结果。
13. 在设计层面预留证书颁发机构权威性 / 正当性标识能力。
14. 将原始路径、相对路径、路径层级、文件名作为类别、地区、人员、资料类型判断的重要参考。
15. [P0] 本地 OCR 应提取完整身份证号，用于人员归并、冲突判断、导出和审计。
16. [P1] 支持一人多证书，查询、导出、待确认和批量操作都必须按多证书关系设计。

### 2.2 不做什么

MVP 阶段暂不做：

1. 不直接上传身份证、学历证、证书原图到云端 AI。
2. 不物理删除原始资料。
3. 不做多用户权限系统。
4. 不做 Web 服务端部署。
5. 不做完整自动化证书合规裁决。
6. 不做 100% 无人工确认的全自动归档。
7. 不强制自动拆分多人员 PDF。
8. 不使用 Rust CLI 作为第一版必要依赖。
9. 不做大规模 RAG 问答。
10. 不强制实现“一人多类别”的完整多对多模型。
11. 不做多类别重复归档，即一个人员自动复制到多个类别目录。
12. MVP 不做完整证书颁发机构权威性库，仅在数据模型中预留字段。

## 3. 用户角色

### 3.1 资料整理人员

主要使用者。负责：

- 选择资料目录
- 启动扫描
- 查看待确认项
- 修正人员和资料信息
- 生成归档目录
- 查询并导出资料

### 3.2 业务负责人

偶尔使用或查看结果。关注：

- 某地区是否有符合条件人员
- 某类证书人员数量
- 查询结果是否可靠
- 导出资料是否完整

## 4. 技术栈要求

### 4.1 桌面应用

目标平台和基础栈：

```text
Windows 本地桌面应用
Electron
electron-vite
React
TypeScript
pnpm
```

项目初始化建议：

```bash
npm create electron-vite@latest qualidex
```

选择：

```text
Framework: React
Variant: TypeScript
```

### 4.2 本地数据库

采用：

```text
SQLite
sqlite-vec
better-sqlite3，Electron 运行时
node:sqlite，Node 脚本和维护工具优先使用
```

用途：

- SQLite 存储人员、文件、证书、归档、导入批次、待确认项等结构化数据。
- sqlite-vec 存储证书语义向量，用于证书候选召回。

### 4.3 OCR

优先采用本地 OCR 和本地 PDF 工具：

```text
PaddleOCR
Poppler / pdftotext / pdftoppm
```

调用方式：

```text
Electron Main Process
  ↓
调用 Python OCR 脚本或本地 OCR 服务
  ↓
返回 OCR 文本
```

MVP 可以先将 OCR 作为可替换模块实现，不强绑定具体 OCR 引擎。

### 4.4 AI API

AI 只处理 OCR 后文本和结构化上下文，不直接处理原图。

完整身份证号隐私规则：

- [P0] 本地 OCR 可以提取完整身份证号，并写入本地 SQLite。
- [P0] 云端文本 AI 不直接接触完整身份证号。
- [P0] 发给云端 AI 的 OCR 文本应先脱敏，或仅提供身份证哈希、后四位、脱敏显示值。
- [P0] 页面可直接展示完整身份证号；该能力仅限本地应用界面，云端 AI 输入仍必须脱敏。

AI 用于：

1. OCR 后文本结构化抽取。
2. 用户自然语言查询解析。
3. 证书候选分组解释。
4. 证书查询词扩展。

## 5. 核心产品原则

### 5.1 原始资料不动

系统不得移动、覆盖、删除原始资料。

所有归档操作都只作用于新的归档输出目录。

```text
原始资料目录：只读
归档输出目录：系统生成
```

### 5.2 数据库是事实源

系统以数据库中的结构化信息作为事实源。

归档目录只是根据数据库生成出来的结果。

```text
原始文件：不可变来源
数据库：结构化事实源
归档目录：生成结果
```

### 5.3 低置信度必须待确认

以下情况必须进入待确认：

- 未识别人员
- 同名冲突
- 完整身份证号缺失、冲突或与姓名不匹配
- 地区不确定
- 主类别不确定
- 文件类型不确定
- 学历不确定
- 证书名称不确定
- 证书是否认可不确定
- OCR 失败
- 多人员资料无法拆分或无法明确归属
- 同一文件夹内文件归属不一致，需要文件夹级二次归并

### 5.4 AI 只做辅助，不做最终裁决

AI 可以抽取、建议、分组、解释，但最终查询、导出和证书认可应基于：

```text
结构化数据库
人工确认结果
SQL 精确查询
```

### 5.4.1 完整身份证号与隐私边界

完整身份证号是人员归并、同名冲突判断、导出和审计的重要字段。

数据库设计原则：

- [P0] `people.id_card_number` 保存完整身份证号明文，仅限本地 SQLite。
- [P1] 可预留 `id_card_number_encrypted`，用于后续加密存储。
- [P0] `id_card_hash` 用于快速查重和匹配。
- [P0] `masked_display` 用于云端 AI 脱敏输入、导出默认脱敏值和隐私场景展示；本地应用页面可显示完整身份证号。

使用原则：

- [P0] 本地 OCR 可提取完整身份证号，本地服务可用于归并判断。
- [P0] 云端 AI 输入不得包含完整身份证号。
- [P0] 归档文件夹名称不得暴露完整身份证号，仍使用后四位或系统编号。
- [P1] Excel 导出保留 `export_full_id_card` 开关，默认导出脱敏值，用户明确选择后才导出完整身份证号。

MVP 不支持一人多身份证记录。系统只支持从多个文件中提取并归并同一个完整身份证号；如果同一人员出现多个不同身份证号，必须进入待确认，不自动合并。

### 5.4.2 一人多证书

一名人员可以关联多张证书。

设计原则：

- [P0] `licenses` 按证书记录建模，一人可拥有多条证书。
- [P0] 查询和导出必须遍历该人员的全部证书，而不是只取一张证书。
- [P1] 批量操作、冲突提示、证书归属调整要支持多证书场景。
- [P1] 证书展示需要包含证书名称、状态、官方 / 非官方标签、有效期、颁发机构和来源可信度预留字段。

### 5.5 类别的查询与归档分离

系统中“类别”同时存在两个使用场景：

1. 归档类别：用于生成文件夹结构。
2. 查询类别：用于筛选人员结果。

MVP 阶段建议：

- 归档类别保持单主类别。
- 查询类别支持多选。
- 查询多选类别默认采用 OR 逻辑。
- 如果一个人员确实存在多个业务类别，第一版可通过人工确认主类别，其他类别作为候选类别或扩展字段记录。
- 后续如业务强依赖“一人多类别”，再升级为人员与类别多对多关系。

这样可以避免归档目录出现重复复制、同步困难和删除风险。


### 5.6 证书认可状态与颁发机构权威性分离

系统中“证书是否认可”和“颁发机构是否权威 / 正当”不是同一个概念。

例如：

```text
证书名称：消防培训合格证
颁发机构：某某培训学校
```

该证书可能与消防相关，但颁发机构权威性较低，因此业务认可度可能不足。

MVP 阶段：

- 系统继续以证书名称、证书类型、业务人工确认为主要判断依据。
- `licenses` 表预留颁发机构权威性字段。
- 颁发机构权威性不作为 P1 核心筛选条件。
- 低权威性、来源不明或判断不确定的证书应进入待确认或在证书详情中标记。

P2 阶段：

- 支持人工维护颁发机构权威性。
- 支持 AI / 规则辅助识别颁发机构权威性。
- 支持按颁发机构权威性筛选证书或人员。
- 可扩展独立 `issuers` 表，沉淀机构库和机构别名。

### 5.6.1 证书官方 / 非官方人工标签

人员证书需要支持一个独立的官方 / 非官方人工标签。

该标签用于表达业务人员对某个人员证书的手动判断，不等同于证书识别状态，也不等同于颁发机构权威性。

MVP 阶段：

- `licenses` 表预留 `official_status`、`official_status_source`、`official_status_updated_at`。
- 默认值必须为 `null`，页面显示为“未判断”。
- 用户可手动设置为“官方”或“非官方”，也可清空恢复为“未判断”。
- 页面中的证书记录、待确认卡片和查询结果需要显示该标签。
- AI / OCR 不得自动写入“官方”或“非官方”，只能提供证据或提示。

### 5.7 路径名与目录层级是重要信息来源

原始文件路径、相对路径、父级文件夹、文件名和路径层级数组是重要信息来源。

路径信息可以辅助判断：

- 主类别
- 地区
- 人员姓名
- 资料类型
- 证书类型
- 多人员资料迹象

示例：

```text
D:\人员资料\工程\成都\张三\二建证.pdf
```

可解析为：

```json
{
  "path_segments": ["人员资料", "工程", "成都", "张三", "二建证.pdf"],
  "candidate_primary_category": "工程",
  "candidate_region": "成都",
  "candidate_person_name": "张三",
  "candidate_document_type": "license"
}
```

路径信息只能作为判断依据之一，不应单独作为最终裁决。

以下情况需要进入待确认：

- 路径和 OCR 内容冲突
- 路径中类别和文件内容类别冲突
- 路径中地区和证书文本地区冲突
- 路径中人员名和 OCR 人员名冲突
- 路径层级不符合预期
- 文件夹名为“新建文件夹”“资料”“扫描件”等低信息量名称
- 一个 PDF 或图片集合在路径上看似单人，但 OCR 识别出多个人

### 5.8 页面流转与处理完成 CTA

核心页面流转：

```text
导入资料
  ↓
整理资料，OCR / AI / 文件夹级二次归并
  ↓
有待确认项 → 待确认资料页
  ↓
待确认处理完成
  ↓
归档预览
  ↓
查询人员 / 导出结果
```

处理完成后的页面提示：

- [P1] 如果存在待确认项，主 CTA 指向“查看待确认资料”。
- [P1] 如果没有待确认项，主 CTA 指向“生成归档预览”。
- [P1] 归档预览完成后，提示用户可以进入查询 / 导出。
- [P1] 重复文件、失败文件和多人员资料必须有独立提示，不应被展示为普通已处理文件。

## 26. 一句话结论

Qualidex 是一个基于 Electron 的 Windows 本地人员资料治理工具。

第一版采用：

```text
electron-vite + React + TypeScript + SQLite + sqlite-vec + 本地 OCR + 云端文本 AI API
```

核心设计是：

```text
原始文件不动
数据库做事实源
归档目录做生成结果
AI 做辅助理解
路径名和目录层级作为重要候选依据
人工确认处理不确定性
SQL 负责最终查询
查询类别支持多选
归档类别保持单主类别
证书颁发机构权威性作为 P2 能力预留
```

最终实现：

```text
主类别 / 地区 / 人员 / 资料类型
```

的稳定归档结构，并支持新增文件夹、修改、删除、重新归档、条件查询和资料导出。

对于“工程 + 消防员”这类需求：

```text
查询层支持多类别
归档层保持单主类别
数据层使用 primary_category，并预留 person_categories
AI 层返回 categories 数组
UI 层使用多选标签

对于“颁发机构权威性不足 / 正当性不明”的证书：

```text
MVP 层预留 issuer_authority_* 字段
P2 层支持人工标记、AI / 规则识别、机构库沉淀和权威性筛选
```
