# Qualidex 开发补充细则

仓库最高优先级开发入口是 `AGENTS.md`。本文只补充测试、验证和代码组织细则，不能覆盖 `AGENTS.md` 中的硬性产品规则。

## 1. 文档与语言

- 项目文档默认中文，包括任务拆解、开发规则、设计说明和 PRD 补充。
- 代码标识符、类型、文件名和脚本名使用英文。
- UI 文案面向非技术业务用户，默认中文。
- 技术术语可以保留英文，但避免在主 UI 中暴露不必要的实现细节。

## 2. 可测试性

- 复杂规则优先写成纯函数，再接入 IPC 或 UI。
- 文件系统、数据库、OCR、AI 等外部依赖应方便替换或 mock。
- 业务能力优先放在 `electron/services/`，IPC 只做薄封装。
- 共享类型后续集中到 `shared/` 或等价目录，避免长期散落在环境声明文件中。
- 先使用简单清晰的模块边界，避免过早抽象。

## 3. 阶段执行

- P0 验证桌面壳、基础工程链路、只读目录选择、递归扫描、hash 去重、SQLite 基础入库和少量样本文本提取。
- 本阶段允许实现目录选择、只读递归扫描、hash 计算、新增/重复识别、扫描结果展示、基础表写入和扫描逻辑验证。
- 本阶段暂不实现 AI 结构化抽取、正式归档和完整导出。
- 每完成一个小块就运行一次验证命令。
- 不引入与 P0 无关的大型依赖。

## 4. 测试原则

- 纯业务规则优先单测，例如扫描、路径规则、hash、归档路径生成、查询条件解析。
- Main Process 能力优先通过 service 层测试，避免把测试直接绑死在 IPC 上。
- Renderer 组件测试只覆盖关键交互和状态，不追求样式细节。
- E2E 只覆盖核心用户链路，不用 E2E 代替所有单测。
- 每个 P0/P1 功能必须提供至少一种可重复验证方式：verify 脚本、单测或 E2E。

## 5. E2E 预留

- 关键交互控件应保留稳定的 `data-testid`。
- 页面状态应有可观测文本或状态区域，方便 Playwright 等工具断言。
- 避免功能成功只能通过截图或人工视觉判断。
- E2E 优先覆盖选择目录、扫描、待确认、归档预览、查询和导出等主链路。

## 6. 验证原则

- 逻辑变更需要对应 verify 脚本或单测。
- UI / IPC 变更至少运行 `pnpm run lint` 和 `pnpm run build`。
- 涉及桌面启动链路时，短暂运行 `pnpm run dev` 验证 Electron 能启动。
- 验证命令应写入 `package.json` scripts，避免只存在于对话记录。

## 7. Node 脚本与数据库工具

- 编写普通 Node.js 脚本访问 SQLite 前，先读 `docs/node-sqlite-runtime-rules.md`。
- 应用侧可以使用 Electron runtime 编译的 `better-sqlite3`；普通 Node.js 脚本不要直接加载它。
- 开发期数据库查看、清理和一次性修复脚本优先使用 `node:sqlite`，并在脚本说明中标注 Node 22+ 要求。
